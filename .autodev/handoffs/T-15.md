## The write-ahead risk, and what was actually found

Plan step 2's own risk note: "tree-sitter's node type names for the IIFE shapes differ
between the javascript and typescript grammars ... confirm each with a tiny parse dump
before writing the matcher; do not guess." Dumped all four documented IIFE forms, plus
the negative (a helper nested inside an ordinary function), through both grammars via
`Language.load` + `parser.parse(src).rootNode.toString()` (a throwaway script, deleted
after use, matching this shop's own convention for one-off probes).

**Surprise: they do not differ.** For all five shapes, the `javascript` and `typescript`
grammars produced byte-identical parse trees (node types and field names). The one
concrete risk plan step 2 called out turned out not to be real for this specific set of
shapes — worth confirming live anyway, since guessing wrong here would have shipped a
matcher that silently only worked in one grammar.

### Shape 1 — `(function () { ... })()` (the call is OUTSIDE the parens)

sql-gauntlet's own `public/app.js` / `chat.js` shape. Source:
```js
(function () {
  function init() {}
  function render() {}
})();
```
Tree (identical in both grammars):
```
(program (expression_statement (call_expression
  function: (parenthesized_expression (function_expression
    parameters: (formal_parameters)
    body: (statement_block
      (function_declaration name: (identifier) parameters: (formal_parameters) body: (statement_block))
      (function_declaration name: (identifier) parameters: (formal_parameters) body: (statement_block)))))
  arguments: (arguments))))
```
Top-level node: `expression_statement` → `call_expression`, whose `function` field is a
`parenthesized_expression` wrapping a `function_expression`. The IIFE's body is that
`function_expression`'s `body` field, a `statement_block` — recurse into ITS children
exactly like the top-level `program` loop already does.

### Shape 2 — `(function () { ... }())` (the call is INSIDE the parens)

Source:
```js
(function () {
  function init() {}
  function render() {}
}());
```
Tree:
```
(program (expression_statement (parenthesized_expression (call_expression
  function: (function_expression
    parameters: (formal_parameters)
    body: (statement_block (function_declaration ...) (function_declaration ...)))
  arguments: (arguments)))))
```
Top-level node: `expression_statement` → `parenthesized_expression` → `call_expression`,
whose `function` field is the `function_expression` directly (no inner parens this time —
the whole call is wrapped instead of just the function). Same target: the
`function_expression`'s `body` field.

### Shape 3 — `(() => { ... })()` (arrow)

Source:
```js
(() => {
  function setup() {}
})();
```
Tree:
```
(program (expression_statement (call_expression
  function: (parenthesized_expression (arrow_function
    parameters: (formal_parameters)
    body: (statement_block (function_declaration ...))))
  arguments: (arguments))))
```
Identical shape to Shape 1 with `arrow_function` in place of `function_expression`. An
arrow's `body` field can also be a bare expression (no block) when there is no `{ }` —
`childForFieldName('body').type !== 'statement_block'` in that case, and the matcher
must treat that as "nothing to recurse into" rather than crash.

### Shape 4 — `!function () { ... }()` (unary-prefixed)

Source:
```js
!function () {
  function boot() {}
}();
```
Tree:
```
(program (expression_statement (unary_expression
  argument: (call_expression
    function: (function_expression parameters: (formal_parameters) body: (statement_block (function_declaration ...)))
    arguments: (arguments)))))
```
Top-level node: `expression_statement` → `unary_expression` (field `argument`, NOT a
named field for the operator itself — the operator token is an anonymous child, position
0) → `call_expression`, function is the bare `function_expression` (no parens needed once
`!` already disambiguates it from a statement-leading `function` keyword). The locate
doc's own wording is "a top-level expression statement whose expression is a call
(possibly parenthesized / unary-prefixed)" — generic, not `!`-specific — so the matcher
unwraps ANY single leading unary operator over such a call (`!`, `void`, `+`, `-`, `~`,
...), not only `!`. Real code overwhelmingly uses `!`; sql-gauntlet's own fixtures use
none of this family at all (they all use Shape 1 or the UMD variant of Shape 1 below), so
this generalization costs nothing and matches the documented rule as written rather than
narrowing it to the one example given.

### The shape sql-gauntlet's `engine.js` / `xray.js` actually use

Not a fifth shape — Shape 1 with a real parameter and a real argument expression instead
of `()`:
```js
(function (root) {
  ...
})(typeof self !== "undefined" ? self : this);
```
Confirmed this parses to the exact same tree shape as Shape 1 (a `formal_parameters` node
with one child instead of zero; an `arguments` node containing the ternary instead of
being empty) — the matcher must never assume the parameter list or argument list is
empty, only that the `function` field (after unwrapping parens) is a
`function_expression`/`arrow_function`.

### The negative: a helper nested inside an ordinary function

Source:
```js
function outer() {
  function helper() {}
  return helper();
}
```
Tree: `(program (function_declaration name: (identifier) ... body: (statement_block
(function_declaration ...) (return_statement ...))))` — the top-level node itself is a
plain `function_declaration`, never an `expression_statement`, so the IIFE matcher never
even looks at it. This is what "recurse ONE level only" costs nothing extra to guarantee:
the matcher only ever fires on a top-level `expression_statement`, and a `function
outer() {}` is not one.

## The matcher (what `extract.ts` is about to gain)

```ts
function unwrapParens(node: SyntaxNode): SyntaxNode {
  let n = node;
  while (n.type === 'parenthesized_expression' && n.namedChildCount === 1) n = n.namedChild(0)!;
  return n;
}

function iifeBody(stmt: SyntaxNode): SyntaxNode | null {
  if (stmt.type !== 'expression_statement') return null;
  let expr = stmt.namedChild(0);
  if (!expr) return null;
  expr = unwrapParens(expr);
  if (expr.type === 'unary_expression') {
    const arg = expr.childForFieldName('argument');
    if (!arg) return null;
    expr = unwrapParens(arg);
  }
  if (expr.type !== 'call_expression') return null;
  const fn = expr.childForFieldName('function');
  if (!fn) return null;
  const target = unwrapParens(fn);
  if (target.type !== 'function_expression' && target.type !== 'arrow_function') return null;
  const body = target.childForFieldName('body');
  return body && body.type === 'statement_block' ? body : null;
}
```
Wired into `jsSymbols`'s existing top-level loop: for each top-level node, try `iifeBody`
first; on a hit, call the SAME `recordDecl(inner, false)` already used for ordinary
top-level nodes over each of the body's direct children (one level, no further descent),
then `continue`. `jsDoc`'s leading-comment lookup needs no change — the inner nodes are
real AST siblings inside the IIFE's own `statement_block`, so "the comment immediately
above the declaration" already resolves correctly without any awareness that it is
sitting one level deeper than usual.
