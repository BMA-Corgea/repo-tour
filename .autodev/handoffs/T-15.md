### The spec tension, and how it was settled

AC2's literal text says "**In both cases** a candidate must be a function/method/class, or
a variable spanning >= 3 lines" — which is what attempt 1 built — while the spec's own
"Out of scope" line said Python and TS/ESM behaviour was "unchanged by design", and the
fallback also newly surfaces private Python symbols and zero-export TS scripts. The spec
was internally in tension, and it has since been corrected. Its out-of-scope line now
reads:

> Python and TS/ESM behaviour **for files that EXPORT something** — unchanged by design (a
> types-only module keeps its interface/type/enum steps; a 1-line exported const keeps its
> step). Files that export nothing take the same exported-or-all fallback as JS — that is
> AC2's language-neutral intent (review finding 2026-09-04).

Both halves of the finding are therefore settled explicitly rather than by silence: the
exported path is restored to exactly T-12's behaviour, and the fallback firing for **any**
language's no-export file is intended, asserted by tests, and disclosed in Surprises 6
below. (The authoritative corrected spec lives in the shop's main checkout; this
worktree's copy under `.autodev/specs/` is the version this branch was cut with and was

### The fix — `3e75bb2`, `src/build/plan.ts`, one branch and one predicate

```ts
const candidates = exported.length > 0 ? exported : symbols.filter(isEligibleCandidate);
```

The filter moved inside the fallback arm. A file that **exports something** now gets the
candidate set T-12 shipped — every exported symbol, any kind, any span — then the same
span sort, overlap-skip and cap of 5. A file that **exports nothing** falls back to all
recorded symbols, screened, which is the only place the screen was ever needed: it exists
to stop the one-line requires and import aliases that the fallback *itself* made eligible.

The predicate was also completed rather than merely re-wired, since `interface` and `enum`
had no business being ineligible even on the fallback path:

```ts
const TRIVIAL_SPAN = 3;
const ALWAYS_ELIGIBLE = new Set<SymbolKind>(['function', 'method', 'class', 'interface', 'enum']);

function isEligibleCandidate(s: SymbolRecord): boolean {
  return ALWAYS_ELIGIBLE.has(s.kind) || s.endLine - s.line + 1 >= TRIVIAL_SPAN;
}
```

`variable` and `type` are the only two `SymbolKind` members not in the set, and they are
exactly the two a one-line alias can be — so the union is covered exhaustively by
construction, and no future kind can fall through to a silent `false` the way three of
them just did. All three docstrings in that region now say which path is which and why,
in both directions.

## The two fixes, in one paragraph each

**`src/extract.ts`** — `jsSymbols()`'s top-level loop now tries `iifeBody(node)` before
falling through to the ordinary `recordDecl(node, false)`. `iifeBody` recognizes a
top-level `expression_statement` that immediately invokes a function/arrow expression —
parens may wrap the call, the function, both, or neither, and a single leading unary
operator is allowed in front (generalized from the ticket's `!`-only example, per the
locate doc's own "unary-prefixed" wording) — and returns that function's
`statement_block` body, or `null` if the shape does not match. On a hit, every direct
child of that body is recorded through the exact same `recordDecl` top-level nodes use,
with `exported` hard-coded `false` (there is no `export` inside a function body) — one
level, never recursed again, so a nested IIFE or a helper inside an ordinary function
stays exactly as invisible as it was before this ticket.

**`src/build/plan.ts`** *(as it stands after the rework — attempt 1's version of this
paragraph described a filter that also ran on the exported path, which was the review's
gating finding; see "Rework (attempt 2)")* — `selectLoadBearing()` computes `exported =
symbols.filter(s => s.exported)` as before. When that list is non-empty the candidates
are exactly it, **unfiltered** — every exported symbol, any kind, any span, precisely
what T-12 shipped. Only when a file exports nothing at all (a plain script, a CommonJS
module, a Python module of `_private` defs, a zero-export TS side-effect script) do the
candidates fall back to every recorded symbol, and only there does
`isEligibleCandidate()` screen them: `function`/`method`/`class`/`interface`/`enum`
always pass, and `variable`/`type` — the only kinds a one-line alias can be — pass only
when `endLine - line + 1 >= 3`, so a one-line `const http = require('http')` never
becomes a step even once "exports nothing" makes everything else in the file eligible.
The screen exists solely to undo the fallback's own side effect, which is why it lives on
the fallback's side of the branch. The span-sort/overlap-skip/cap-5 tail is
byte-unchanged.

## The write-ahead risk, and what was actually found

Plan step 2's own risk note: "tree-sitter's node type names for the IIFE shapes differ
between the javascript and typescript grammars ... confirm each with a tiny parse dump
before writing the matcher; do not guess." Dumped all four documented IIFE forms, plus
the negative (a helper nested inside an ordinary function), through both grammars via
`Language.load` + `parser.parse(src).rootNode.toString()` (a throwaway script, deleted
after use, matching this shop's own convention for one-off probes).

**Surprise: they do not differ.** For all five shapes, the `javascript` and `typescript`
grammars produced byte-identical parse trees (node types and field names). The one
concrete risk plan step 2 called out turned out not to be real for this specific set of
shapes — worth confirming live anyway, since guessing wrong here would have shipped a
matcher that silently only worked in one grammar.

### Shape 1 — `(function () { ... })()` (the call is OUTSIDE the parens)

sql-gauntlet's own `public/app.js` / `chat.js` shape. Source:
```js
(function () {
  function init() {}
  function render() {}
})();
```
Tree (identical in both grammars):
```
(program (expression_statement (call_expression
  function: (parenthesized_expression (function_expression
    parameters: (formal_parameters)
    body: (statement_block
      (function_declaration name: (identifier) parameters: (formal_parameters) body: (statement_block))
      (function_declaration name: (identifier) parameters: (formal_parameters) body: (statement_block)))))
  arguments: (arguments))))
```
Top-level node: `expression_statement` → `call_expression`, whose `function` field is a
`parenthesized_expression` wrapping a `function_expression`. The IIFE's body is that
`function_expression`'s `body` field, a `statement_block` — recurse into ITS children
exactly like the top-level `program` loop already does.

### Shape 2 — `(function () { ... }())` (the call is INSIDE the parens)

Source:
```js
(function () {
  function init() {}
  function render() {}
}());
```
Tree:
```
(program (expression_statement (parenthesized_expression (call_expression
  function: (function_expression
    parameters: (formal_parameters)
    body: (statement_block (function_declaration ...) (function_declaration ...)))
  arguments: (arguments)))))
```
Top-level node: `expression_statement` → `parenthesized_expression` → `call_expression`,
whose `function` field is the `function_expression` directly (no inner parens this time —
the whole call is wrapped instead of just the function). Same target: the
`function_expression`'s `body` field.

### Shape 3 — `(() => { ... })()` (arrow)

Source:
```js
(() => {
  function setup() {}
})();
```
Tree:
```
(program (expression_statement (call_expression
  function: (parenthesized_expression (arrow_function
    parameters: (formal_parameters)
    body: (statement_block (function_declaration ...))))
  arguments: (arguments))))
```
Identical shape to Shape 1 with `arrow_function` in place of `function_expression`. An
arrow's `body` field can also be a bare expression (no block) when there is no `{ }` —
`childForFieldName('body').type !== 'statement_block'` in that case, and the matcher
must treat that as "nothing to recurse into" rather than crash.

### Shape 4 — `!function () { ... }()` (unary-prefixed)

Source:
```js
!function () {
  function boot() {}
}();
```
Tree:
```
(program (expression_statement (unary_expression
  argument: (call_expression
    function: (function_expression parameters: (formal_parameters) body: (statement_block (function_declaration ...)))
    arguments: (arguments)))))
```
Top-level node: `expression_statement` → `unary_expression` (field `argument`, NOT a
named field for the operator itself — the operator token is an anonymous child, position
0) → `call_expression`, function is the bare `function_expression` (no parens needed once
`!` already disambiguates it from a statement-leading `function` keyword). The locate
doc's own wording is "a top-level expression statement whose expression is a call
(possibly parenthesized / unary-prefixed)" — generic, not `!`-specific — so the matcher
unwraps ANY single leading unary operator over such a call (`!`, `void`, `+`, `-`, `~`,
...), not only `!`. Real code overwhelmingly uses `!`; sql-gauntlet's own fixtures use
none of this family at all (they all use Shape 1 or the UMD variant of Shape 1 below), so
this generalization costs nothing and matches the documented rule as written rather than
narrowing it to the one example given.

### The shape sql-gauntlet's `engine.js` / `xray.js` actually use

Not a fifth shape — Shape 1 with a real parameter and a real argument expression instead
of `()`:
```js
(function (root) {
  ...
})(typeof self !== "undefined" ? self : this);
```
Confirmed this parses to the exact same tree shape as Shape 1 (a `formal_parameters` node
with one child instead of zero; an `arguments` node containing the ternary instead of
being empty) — the matcher must never assume the parameter list or argument list is
empty, only that the `function` field (after unwrapping parens) is a
`function_expression`/`arrow_function`.

### The negative: a helper nested inside an ordinary function

Source:
```js
function outer() {
  function helper() {}
  return helper();
}
```
Tree: `(program (function_declaration name: (identifier) ... body: (statement_block
(function_declaration ...) (return_statement ...))))` — the top-level node itself is a
plain `function_declaration`, never an `expression_statement`, so the IIFE matcher never
even looks at it. This is what "recurse ONE level only" costs nothing extra to guarantee:
the matcher only ever fires on a top-level `expression_statement`, and a `function
outer() {}` is not one.

## The matcher (landed in `ed9b731`, verbatim)

```ts
function unwrapParens(node: SyntaxNode): SyntaxNode {
  let n = node;
  while (n.type === 'parenthesized_expression' && n.namedChildCount === 1) n = n.namedChild(0)!;
  return n;
}

function iifeBody(stmt: SyntaxNode): SyntaxNode | null {
  if (stmt.type !== 'expression_statement') return null;
  let expr = stmt.namedChild(0);
  if (!expr) return null;
  expr = unwrapParens(expr);
  if (expr.type === 'unary_expression') {
    const arg = expr.childForFieldName('argument');
    if (!arg) return null;
    expr = unwrapParens(arg);
  }
  if (expr.type !== 'call_expression') return null;
  const fn = expr.childForFieldName('function');
  if (!fn) return null;
  const target = unwrapParens(fn);
  if (target.type !== 'function_expression' && target.type !== 'arrow_function') return null;
  const body = target.childForFieldName('body');
  return body && body.type === 'statement_block' ? body : null;
}
```
Wired into `jsSymbols`'s existing top-level loop: for each top-level node, try `iifeBody`
first; on a hit, call the SAME `recordDecl(inner, false)` already used for ordinary
top-level nodes over each of the body's direct children (one level, no further descent),
then `continue`. `jsDoc`'s leading-comment lookup needs no change — the inner nodes are
real AST siblings inside the IIFE's own `statement_block`, so "the comment immediately
above the declaration" already resolves correctly without any awareness that it is
sitting one level deeper than usual.

## Surprises, in the order they were found

1. **The write-ahead risk did not materialize.** Plan step 2 flagged the javascript vs.
   typescript grammars as a likely source of divergent node names for the IIFE shapes.
   Dumped all four shapes (plus the negative) through both grammars before writing any
   matcher: the trees are byte-identical, field names included. One matcher serves both
   grammars with no per-grammar branching. Documented in full above so the next person
   who assumes grammar drift here can check this record instead of re-deriving it.
2. **The locate doc's own wording ("unary-prefixed") is broader than the ticket's single
   named example (`!function(){}()`).** Implemented the general rule (any single leading
   unary operator over a call to a function/arrow expression) rather than special-casing
   `!` — real-world code overwhelmingly uses `!` anyway (sql-gauntlet's own fixtures use
   none of this family at all), so this costs nothing and avoids under-implementing the

### Added in the rework — the disclosure this section was missing

6. **The exported-or-all fallback fires in EVERY language, not just JS — and that is
   intended, not a side effect.** This is the half of the review's gating finding that is
   a *disclosure* gap rather than a code defect, and attempt 1's version of this section
   never mentioned it. `selectLoadBearing` is language-neutral: it sees `SymbolRecord[]`
   and an `exported` boolean, and has no idea which grammar produced them. So "this file
   exports nothing, therefore every recorded symbol is a candidate" applies to:
   - **Python modules whose top-level defs are all `_private`.** `extract.ts` sets
     `exported: !name.startsWith('_')`, so such a module has zero exported symbols, the
     fallback fires, and its `_helper` functions now get symbol steps where before the
     file got none. Verified live, asserted by rework test (c).
   - **TS/ESM files with no `export` at all** — side-effect scripts, registration
     modules, `bin/` entrypoints. Same mechanism; asserted by rework test (d).
   - Anything else with recorded symbols and no export, in any language the extractor
     grows later.

   This is AC2's language-neutral intent, now stated as such in the corrected spec's
   out-of-scope line (quoted in full in "Rework (attempt 2)" above). Practically it means
   a Python-heavy or script-heavy repo will mint MORE symbol steps than before this
   ticket, up to the same cap of 5 per file — which is the point (a file with no
   load-bearing ranges teaches nothing), but it is a real, visible output change for
   repos that have nothing to do with sql-gauntlet's IIFEs, and anyone diffing plans
   across this ticket should expect it.

7. **A closed union with an open-ended `return false` is how three kinds went missing.**
   Attempt 1's `isEligibleCandidate` enumerated `function`/`method`/`class`/`variable`
   and returned `false` for everything else — which silently swallowed
   `interface`/`type`/`enum`, three of `SymbolKind`'s seven members, on every path.
   Nothing type-checked wrong, nothing failed, and no test looked. The rework inverts the
   default: `ALWAYS_ELIGIBLE` is a `Set<SymbolKind>` and the only fall-through is the
   span test for the two kinds deliberately left out of it, so adding an eighth
   `SymbolKind` later cannot silently make it ineligible. Worth remembering the next time
   a predicate over a closed union in this codebase ends in `return false`.
