### Gating finding: `isEligibleCandidate` is not scoped to the fallback branch, and measurably changes TS/ESM and Python behavior the spec calls out-of-scope

`src/build/plan.ts:245`:
```ts
const candidates = (exported.length > 0 ? exported : symbols).filter(isEligibleCandidate);
```
The triviality filter runs over **both** branches — the pre-existing "candidates are the
exported symbols" path, not only the new "file exports nothing" fallback. Concretely, with
`main`'s `plan.ts` swapped in against the *same* fixtures:

| Fixture (all real exports, fallback never triggers) | `main` (pre-T-15) | This branch |
|---|---|---|
| TS file exporting only `interface Widget {...}`, `type WidgetId = string`, `enum WidgetKind {...}` | 3 symbol steps (`Widget`, `WidgetId`, `WidgetKind`) | **0** |
| TS file exporting only `export const PI = 3.14159;` (1 line) | 1 symbol step (`PI`) | **0** |

And in the other direction, the fallback fires for languages/files the spec says are
unaffected:

| Fixture | `main` (pre-T-15) | This branch |
|---|---|---|
| Python file with only `_private` top-level defs (all `exported: false`) | 0 symbol steps | **2** (`_helper_one`, `_helper_two`) |
| TS file with zero `export` statements, real top-level functions | 0 symbol steps | **1** (`registerGlobal`) |

`SymbolKind` (`src/types.ts:59`) includes `interface`/`type`/`enum` as first-class kinds
alongside `function`/`method`/`class`/`variable`; `isEligibleCandidate` (`plan.ts:223-228`)
only allows `function`/`method`/`class` unconditionally and `variable` conditionally —
`interface`/`type`/`enum` fall through to `return false` unconditionally, in *every* branch,
not only the fallback. Before this ticket, `selectLoadBearing` had no kind filter at all: any
exported symbol was a candidate.

This is a real, verified regression for an entire class of ordinary TypeScript files (any
module whose public surface is types — a `types.ts`, an `interfaces.ts`, a file exporting one
short constant) that were never mentioned in this ticket's symptom, touched set, or acceptance
criteria's motivating example, and it directly contradicts the spec's own text
(`.autodev/specs/T-15-script-symbols.md`, "Out of scope: … Python and TS/ESM behaviour —
unchanged by design"). None of T-12's 49 existing fixtures, and none of the 9 new
`build-scripts.test.ts` cases, exercise an exported-interface/type/enum-only file, a short
exported constant, a private-only Python file, or a zero-export TS file — so nothing in the
green suite would catch this, and it is not mentioned anywhere in the handoff's otherwise
thorough "Surprises" section.

To be fair to the builder: AC2's own literal text — "candidates are the exported symbols…
**In both cases** a candidate must be a function/method/class, or a variable spanning >= 3
lines" — does say "in both cases," which is exactly what got built. The spec is internally
in tension (AC2's literal words vs. the "Out of scope" line a few paragraphs later), and the
implementation followed the AC. That tension is a spec defect as much as an implementation
one, but the burden was on the builder to surface a change of this size (loses steps on a
whole class of real files; gains steps on two languages/situations the spec explicitly
excludes) rather than let it ride silently under "in both cases." **This needs an explicit
decision — scope `isEligibleCandidate` to the fallback branch only (matching "unchanged by
design"), or get the spec's out-of-scope line corrected and add tests for the now-intended
Python/TS-script behavior — not silence.** Classed gating because it is reproducible, has
real blast radius on ordinary repos, and is asserted nowhere.

No waiver granted — this is not the reviewer's call to make unilaterally; it needs either a
code fix or an operator/PM decision reconciling the spec text before this can pass.
